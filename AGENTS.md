## UX rules

1. Do not use em dashes in text.
2. Do not use background gradients.
3. Do not put `<span>` above `<h1>`, `<h2>`, `<h3>`, or `<strong>`.
4. Do not use star emoji. Create an SVG instead.
5. Do not use outlines on buttons or input elements, including dropdown triggers and options. Do not imitate an outline with a border or box-shadow ring. Show keyboard focus with a visible background or foreground change instead.
6. Use a custom, minimal or Apple-style scrollbar.
7. Do not put an eyebrow above a title.
8. Use animated transitions where applicable.
9. Provide standard keyboard shortcuts, including Enter, Escape, and Command + K.
10. Choose a loader from the approved beUI-inspired inventory: Spinner for general loading, Dots for thinking states, and ASCII for CLI or CLI-like interfaces. Read [the loader inventory](references/loaders.md) and copy the ready-made components from `assets/loaders/` into the existing project. Do not install beUI, Motion, or a UI library for these loaders. Visual source: https://beui.dev/components/motion/loader (`spinner`, `dots`, and `ascii` variants). Keep the source attribution. Inherit the foreground colour, scale web loaders to their context, and reuse shared components. Provide accessible loading labels and respect reduced-motion preferences: Spinner and Dots use opacity pulses instead of movement; ASCII slows its glyph cycle. Apply rule 29 for centred placement and stable web loading layouts. Use other loader styles only when the user requests them.
11. Create a custom SVG logo if no logo is supplied.
12. Prefer icons to text for actions. Prefer toggles for state changes. For example, change a copy icon to a check mark.
13. Provide deep links for suitable actions. Keep the state after a page refresh.
14. Make breadcrumb text a link.
15. Set buttons with no function to 0.5 opacity. On hover, show a tooltip that explains their purpose.
16. Provide dark and light modes. Use dark mode by default.
17. Give layout options for the product. Recommend one option.
18. Do not show large statistics on the front page unless it is a dashboard or the user requests them.
19. Prefer a main-content maximum width of 896 px. For dashboards, use a Pinterest-style card layout.
20. Avoid `chip__label` on dashboards unless it identifies list items or data types.
21. Avoid `border-left: 2px solid <colour>` on sections and cards.
22. Take and inspect screenshots of the affected UI in the running app. Check that no content extends outside its container and that the centring requirements in rule 23 are met. Check selected and unselected header items, icon-only controls, labels with badges, and expanded and collapsed navigation rails wherever those states apply. Fix visible misalignment and inspect a new screenshot before marking the UI work complete. If the running app or screenshots are unavailable, report that visual alignment remains unverified.
23. Centre icons, labels, and badges vertically and horizontally within their own buttons, tabs, badges, and navigation slots. Align header items along a shared vertical centreline, including controls with different heights and labels paired with badges. In a collapsed left navigation rail, centre each control horizontally within the rail and centre its icon on both axes within the control. In an expanded rail, vertically centre icons and labels within each row while keeping labels left-aligned. Centre the contents of each control, not the entire header or navigation group. Use layout alignment and consistent control dimensions rather than arbitrary offsets. Account for font line-height and SVG viewBox whitespace; inspect the visible text and icon alignment, not only their bounding boxes.
24. Use client-side routing.
25. Do not use visible borders on UI elements, including cards, sections, buttons, and input fields. Thin structural separators between workspace panels and panes are permitted; do not use them as decorative element borders or focus rings.
26. Status text must be coloured.
27. When provider, adapter, or client configurations appear in the UI, read [the provider icon inventory](references/provider-icons.md) and reuse matching SVGs or the ready-made React component from `assets/provider-icons/` first. Do not install an icon library for bundled icons or redraw an existing brand icon. Preserve source attribution and distinguish brand icons from custom client glyphs. For a missing icon, reuse an existing project asset or find an official SVG before creating a neutral custom glyph; do not invent a brand logo. Centre each icon vertically and horizontally within its container and verify visibility in dark and light modes.
28. For an app studio, set the application header height to 43 px. If there is a left navigation rail, set its collapsed width to 51 px. Set the icons inside the rail to 35 by 35 px. Centre the icons vertically and horizontally within their containers. Give each icon a tooltip that identifies its function. Use Command + B to expand and collapse the left navigation rail. Put the app icon at the far left of the header, inside the navigation area. Put the expand/collapse toggle in the header, immediately outside the navigation area’s right edge. Leave a small gap between the edge and the toggle. Keep the toggle aligned with this edge in both expanded and collapsed states. Do not group it directly beside the app icon.
29. Keep the layout stable during loading. Reserve the space for pending content with a placeholder that matches its expected size and position. Centre a loading spinner vertically and horizontally within the placeholder. A skeleton is optional. Do not let missing content, loading indicators, or loaded content cause layout shifts or restructure the surrounding content.
30. Prefer inline editing. Compare current values with the last saved values to detect unsaved changes. Show the island only while they differ, and hide it if the original values are restored. Clicking outside an inline edit field or moving focus away deactivates the field and displays the draft as normal text; preserve unsaved changes for Save or Discard rather than silently saving or discarding them. When unsaved changes are detected, show a floating action panel at the bottom centre of the screen. Show coloured status text for unsaved changes and provide Save and Discard actions. Include Delete for an existing item, keep it separate from Save and Discard, and ask for confirmation before deletion. Save applies the changes. Discard cancels the changes. Hide the panel after a successful save or discard. The panel must not move, resize, or restructure the page content.
31. Use syntax highlighting for all code displayed in the UI.
32. After a successful copy action, change the copy icon to a green tick.
33. Input fields must have a different background colour from the form background. Apply this rule in both dark and light modes.
34. When creating a local Electron app, make sure all interactive elements in the header are clickable. If the header has a window-drag region, apply `-webkit-app-region: no-drag` to header buttons, links, inputs, and other interactive controls so the drag region does not block clicks. Verify the controls in the running Electron app, not only in a browser preview.
35. Avoid stacked decorative containers around content previews. Use one card surface instead of nested backgrounds, rounded frames and repeated padding. Let images and video fill the card preview area, with padding reserved for text, metadata and controls. Keep structural wrappers only when needed for layout, scrolling, loading or accessibility; they should not introduce another visible box. In full-content modals, use one viewer surface and preserve the original media proportions.
36. For dropdown buttons and select menus, reuse the approved [dropdown reference](references/dropdowns.md) and bundled example in `assets/dropdowns/`. Keep the label, leading icon and trailing chevron on one vertical centreline. Place the chevron in a fixed slot at the right edge, independent of label length; centre its SVG on both axes and truncate long labels before that slot. Use exactly one background highlight within an open menu, with the same colour for pointer and keyboard navigation. On opening, highlight the committed choice. Move the highlight with pointer hover or Up/Down without changing the committed choice or its tick. Move the tick only after click or Enter commits an option; Escape closes without committing. Use background changes for focus, with no outline, border or shadow ring on the trigger or options. Preserve stable layout, accessible names and keyboard operation; verify compact and standard controls, long labels, open/closed states and dark/light modes in screenshots.
37. For left navigation rails, reuse the approved [navigation rail reference](references/navigation-rail.md) and bundled example in `assets/navigation-rail/`. Apply rule 28: a 43 px header, 51 px collapsed rail and 35 by 35 px control slots. Use one horizontal centreline for the app logo, navigation icons, label swatches, section add buttons and More/Less chevrons in collapsed mode. Scrollbars must not consume slot space, shift this centreline or clip controls. In expanded mode, vertically centre icons, labels, counts and row actions; keep labels left-aligned and truncate long names before counts and actions. Reserve the action slot so hover does not move text. For a 35 px row, centre a 25 px action button with equal 5 px top, bottom and right insets; align section + buttons with the row action centreline. Keep section titles and structural separators consistent. Hide titles and counts when collapsed; preserve add actions and provide tooltips and accessible names. Animate expansion/collapse and More/Less without rebuilding the toggled content. More points down; Less points up, with a centred rotating chevron. Respect reduced motion. Verify both modes, scrolling and both themes visually before completion.
38. Provide row context menus through the action button and right-click in expanded and collapsed navigation. Reuse the [navigation rail reference](references/navigation-rail.md). For editable labels, include Rename, Change colour and a separate Delete action with confirmation. Keep menu icons and text vertically centred with consistent item padding. Use a single background highlight that follows pointer or keyboard navigation, with no outline or focus ring. Support Up/Down, Home/End, Enter, Escape and normal Tab navigation. Escape closes and returns focus to the invoking control. Place the menu within the viewport and above clipping containers without shifting the surrounding layout.
39. For editable label colours, provide both preset swatches and a custom colour picker with a validated hex input. Reuse the [navigation rail reference](references/navigation-rail.md). Show exactly one tick for the current colour: on its preset, or beside the custom colour when no preset matches. Give colour controls accessible names and keep the tick centred. Preview colour changes in expanded and collapsed label icons without moving or resizing the rows. Keep the Save/Discard island visible while the draft differs from the saved colour; Save commits and Discard restores the saved colour. Invalid hex input must show an explanation and prevent saving. Use background changes for focus, with no outlines, borders or shadow rings.
40. For right workspace panels, reuse the approved [right panel reference](references/right-panel.md) and bundled example in `assets/right-panel/`. Use a thin structural divider between the main workspace and panel, and between panes. Keep the panel header 43 px high and centre 35 px controls along the same vertical centreline. Use distinct icons for the open-tabs list and panel visibility toggle. Show/hide the panel with Command + Shift + B on macOS or Control + Shift + B elsewhere, and show the shortcut in its tooltip. Support expand/restore and adjustable panel width. Preserve tabs, drafts, active views and pane layout when hiding or restoring the panel.
41. Animate right-panel opening and closing with a smooth horizontal slide, retaining the panel width and content geometry during the movement. Animate the main workspace width alongside it. Prevent focus and tab visibility handling from scrolling the outer workspace or causing a jump; use focus with preventScroll and scroll only the tab strip. Clip sliding content without creating a programmatically scrollable outer container. Respect reduced motion. Verify repeated toggles, both directions, expanded/restored states and both themes in the running example.
42. Right workspace panels must support a persistent pane tree with horizontal, vertical and nested splits. Each pane has its own tab strip, one active tab highlight and independent content scrolling. Drag tabs into another pane's tab bar to move or reorder them; drag to its left, right, top or bottom edge to create a split. Show a clear drop preview and allow Escape to cancel. Resize pane widths and heights through draggable dividers, with minimum usable sizes and keyboard adjustment. Preserve each tab's content, scroll position, draft and embedded view during moves rather than remounting it. Remove empty panes and let their neighbour fill the space. Provide accessible split controls and keyboard alternatives.
43. Provide a right-click Close pane action for right workspace panes. Closing a pane merges all its tabs into a neighbouring pane, retaining tab order, drafts and content; it must not close those tabs. Prefer a sibling pane in the same split, collapse the empty split and focus the moved active tab. Keep at least one pane open and disable Close pane with an explanation when it is the only pane. Keep the context menu inside the viewport, support keyboard operation and persist the merged layout.
44. For editable tables, reuse the approved [table reference](references/tables.md) and bundled example in `assets/tables/`. Keep column widths, row heights and control slots stable when entering or leaving editing, sorting or validation states. Align headers with their values; right-align numeric values using tabular numerals. Reserve space for sort indicators, dirty markers, disclosure buttons and row actions so they do not move neighbouring content. Centre checkboxes, chevrons and action icons. Keep unchecked checkboxes clearly visible against idle, hovered and selected row backgrounds in both themes; strengthen their fill on hover and keyboard focus without adding an outline. Represent partial selection with an indeterminate mark. Keep headers sticky inside the table's own scrolling container.
45. Inline table editing must activate only from the value and its small surrounding padding, or an explicit edit control. Empty cell space and ordinary row clicks must not start editing. Keep keyboard activation available and use suitable text, number, date and choice editors. Enter finishes an edit; Tab and Shift + Tab move between editable values; Escape restores the value from the start of that cell edit. Clicking away exits editing and displays the unsaved draft as normal text. Apply rule 30 for dirty detection and the Save/Discard island. Validate values with a visible explanation, retain invalid drafts and block Save while errors remain. Validation must not change row heights. Keep row selection, expansion, editing and row actions as separate targets.
46. Sort table data by its underlying type, including numeric amounts and dates, rather than formatted display strings. Use stable row IDs and deterministic ordering for ties. Show the active sort direction in a reserved slot and expose it with aria-sort. Clicking a sortable header changes direction; provide a way to restore the original order. Keep a row in place while the user types so it does not move under their cursor; reposition it only after an explicit sorting action or an appropriate completed action. Preserve drafts, selection and expanded-row identity through sorting and filtering. Choice editors follow rule 36, with one active background highlight and a tick that stays on the committed choice until activation.
47. Provide table and card views for suitable record collections, sharing the same records, drafts, sorting, selection, validation and expanded state. Recommend cards by default on mobile unless the user has chosen another view; remember that choice. Use a single card column, readable field labels and at least 44 px mobile interaction targets. Keep table view available with horizontal scrolling inside its container; the table must not widen the page. Keep sorting and other core actions available in every view. Verify mobile editing, menus, the action island and both themes without clipping.
48. Show expandable row details beneath the corresponding table row, and beneath the fields in card view. Use an independent disclosure control with aria-expanded and aria-controls. Animate both opening and closing through the actual content height, with a centred chevron that rotates from right to down. Keep the detail wrapper mounted while toggling so collapse can animate; collapsed content must not be focusable or exposed as visible to assistive technology. Associate expansion with the record ID through sorting and view changes. Stack detail sections vertically on mobile. Respect reduced motion and verify both transition directions.
49. Refresh controls must visibly spin during loading at 0.8 icon opacity and block repeated activation while busy. Use correctly centred SVG circle geometry and rotate around the SVG viewBox centre so the circle stays in one place. On successful completion, morph the refresh shape smoothly into a green tick rather than abruptly swapping icons. Keep the control's dimensions and centre fixed through the morph, and keep the tick green on hover and keyboard focus. Show a distinct failure/retry state. Expose busy and completion status accessibly, preserve existing content and unsaved drafts during refresh, and avoid layout shifts. For reduced motion, use the approved opacity-based loading treatment and skip the geometric morph. Reuse the state examples and morph in the [table reference](references/tables.md).
50. For inbox and investigation workflows, reuse the approved [master-detail reference](references/master-detail.md) and self-contained examples in `assets/master-detail/`. Use two columns beneath a shared toolbar: a scrollable master list about one-third wide and a detail workspace about two-thirds wide. Keep the list visible while inspecting records on desktop. Separate panes with a thin structural divider and support pointer and keyboard resizing with usable minimum widths. Scroll the list and detail independently without widening the page. Keep search, filters and suitable view switches above the list. Preserve selection and drafts across filtering, view changes and navigation; use stable record IDs and deep links.
51. Keep inbox cards a consistent height within each view and breakpoint. Reserve equal slots for the sender or title, timestamp, subject, preview, and optional status or attachment indicators. Clamp long subjects and previews to a fixed number of lines, and retain the reserved space when text is shorter or metadata is absent. Missing badges or attachments must not shrink a card. Keep avatars, timestamps and metadata aligned across cards, with no clipping or text overlap. Apply this to list and grouped board views; verify short and long content, selected and unselected cards, and records with and without indicators in both themes and on mobile. Adapt the slot size to the product rather than copying one fixed pixel height everywhere.
52. Adapt master-detail content to the use case while retaining the shared structure and transitions. For report triage and investigation, show submission details and report actions, preview alongside category/work/AI status, editable findings, attachments alongside reproduction steps, claim ownership, and Resolve/Dismiss actions. Apply rule 30 to draft changes and deletion. For email, show sender, recipient, date, subject and message body, attachment previews, and a reply draft; provide suitable read/unread and archive actions. Preserve drafts when switching records and show the Save/Discard island only while they differ from saved values. Keep attachments on one preview surface, display filename/type/size where available and open media in a proportional viewer. Clearly identify local demo actions; saving a demo draft must not imply that an email was sent.
53. On narrow screens, use an animated master-to-detail drilldown with a clear Back to inbox action. Preserve the selected record, drafts and list position when returning. Keep hidden panes inert so their controls cannot receive focus. Stack detail sections and wrap metadata without horizontal page overflow; provide at least 44 px mobile action targets. Support Up/Down for list navigation, Enter to inspect, Escape to return or dismiss the active viewer, and Command/Control + K for search. Respect reduced motion. Verify opening and closing transitions, independent scrolling, attachment previews, resizing, draft retention, and desktop/mobile layouts in dark and light modes before completion.
54. For app studios that should feel framed, reuse the approved [outer frame studio reference](references/outer-frame.md) and bundled example in `assets/outer-frame/`. Place the header, navigation rail, brand cell and footer directly on a flat outer frame with no fill or dividers. Put the workspace and the optional right panel in separate rounded inset cards (about 12 px radius) with an 8 px gap between the cards and to the window edge; the gap replaces the workspace/panel divider of rule 40, and cards have no visible borders. Use frame tones for hover and selected states of controls on the frame and surface tones for controls inside cards, so highlights stay visible in both themes. Keep rule 28 and 37 geometry. Animate rail and panel changes through the grid columns, keep the panel card at a fixed width inside a clipping container while it slides, and make the hidden panel inert. Scroll view content inside the workspace card only. Read the route from the URL before rewriting it so refresh and deep links keep the view. Verify the collapsed-rail centreline, toggle offset, card gaps with the panel open and closed, and both themes in screenshots.
55. Give rows, buttons, chips, inputs and cards balanced inner padding. Trailing content such as counts, badges, keyboard hints, chevrons and row actions must never touch the container edge or the edge of its hover, selected or focus highlight. Inset it by the same visible distance as the leading icon or text on the opposite side. In a 35 px row with a 35 px leading icon slot, place a trailing count or action in a 35 px trailing slot so leading and trailing centres mirror each other; without a leading icon, keep at least 8 px horizontal padding inside the highlight. Keep the same insets in every state and in expanded and collapsed layouts. Check insets against the visible highlight background in screenshots, not only the bounding box.
56. For admin and configuration interfaces, reuse the approved [admin reference](references/admin-layout.md) and self-contained example in `assets/admin-layout/`. Avoid mixed purpose and weak hierarchy: give each page one primary job, group related settings under clear section titles and descriptions, and separate configuration from operational records, credentials, access policies and delivery history. Use navigation for distinct domains and tabs for sections within one domain. Do not combine report investigation, agent credentials and workspace settings into one long form. Keep summaries compact and place advanced options after essential configuration.
57. Use a persistent admin shell with a shared header, left navigation and one right content area. Render Reports and other operational pages inside that content area rather than creating a disconnected second shell or placing the page in the navigation column. Keep one current navigation item and one active tab per group. Use distinct icons for different destinations. Preserve suitable page, tab, record and scope deep links through refresh. Apply the existing rail geometry, alignment, transitions and keyboard rules; keep the content within its container on desktop and mobile.
58. Organise common SaaS configuration into appropriate General, Workspace, Members, Billing, Security, Notification preferences and Integration/API sections. Keep workspace defaults separate from individual user overrides and human access separate from agent credentials. Show labels, short explanations and controls in consistently aligned rows, with distinct input backgrounds in both themes. Use toggles for states and the approved selects for choices. Keep connected-resource setup and operational histories in their own pages, linked from relevant settings. Apply rule 30 to drafts, visible validation and Save/Discard; do not imply that local demo billing or security controls perform real operations.
59. Model providers belong in a dedicated Models/Providers page, with add/manage connections, provider-specific authentication or endpoint configuration, connection status/testing and model choices. General settings should choose a model from configured, enabled connections and link to provider management rather than using an isolated provider name plus Configure action. Support major hosted providers and local runtimes including LM Studio and Ollama, plus a clearly identified custom compatible endpoint. Reuse genuine provider logos from rule 27 and the admin reference inventory in the picker, selected trigger and connection list. Never replace an existing brand with a generic glyph; retain attribution and verify logo contrast in both themes.
60. Treat API product management as a separate domain: select a product, curate which underlying operations it exposes, select the applicable workspace/scope, grant client access, and configure policies and quotas. Separate API catalogue/exposure, client access, usage and product settings into clearly named sections or tabs. Distinguish REST, MCP and other supported external surfaces where relevant. Keep operation publication, consumer grants and policy controls separate from model-provider credentials and agent permissions. Use stable IDs and deep links for product, tab and scope, preserve draft selections, validate quotas and explain the effective access represented by each control.
61. Storage pages should distinguish usage breakdown, backup history/configuration, retention and maintenance routines. Show compact used/available capacity, a readable breakdown by content type, and sortable/filterable records with filename, type, size and relevant details. Align numeric sizes, preserve record identity and contain scrolling. Give cleanup actions a review of eligible items and reclaimed space before confirmation; make protected/excluded data clear. Keep retention policy configuration separate from immediate cleanup. Reuse the admin storage example and existing table, preview and loading rules.
62. Backup and routine configuration should show enable/pause state, frequency, time, timezone, conditional weekday, destination and relevant destination fields, content scope, retention and failure notifications. Reveal fields only when applicable and validate the active configuration. Keep recovery-point history and status separate from configuration, with manual-run progress and failure/retry states. Require saved valid settings before running against that configuration. Explain restore scope and destination before confirmation, preserve existing data and drafts during progress, and keep simulated runs clearly identified. Routine configuration should distinguish backup scheduling from integrity checks, usage checks and retention/cleanup tasks.
63. Notification preferences should distinguish delivery channels, subscribed event types, immediate/digest timing and quiet hours. Provide per-event channel controls; disabling a channel disables its controls while retaining their preferences. Validate recipient addresses and applicable schedule values, support timezone and overnight quiet hours, and explain urgent-event overrides where provided. Keep preference editing separate from the notification inbox and delivery history. Tests show accessible loading and success/failure states and must clearly identify simulated delivery.
64. Provide notification access through both a top-right bell and a left navigation destination, with a dedicated notification page. Show unread count in a centred circular red badge on the bell; hide it at zero and cap large counts consistently. Hovering or focusing the bell opens a viewport-contained preview that remains usable while moving into it; clicking or tapping the bell opens that preview. Clicking a preview item opens the notification page at that item and marks it read, reducing the shared count. Support read/unread, mark all read, All/Unread filters and an empty state; persist read state separately from settings drafts. Keep previews and inbox rows aligned and consistent, support keyboard operation and Escape, and provide touch/mobile access without relying on hover.
65. Use a users table for workspace access administration, with stable summary rows for avatar/name, email, role, account state and effective capability count. Use an independent centred disclosure control to expand extra configuration beneath the corresponding user. Apply rules 44–48: animate both directions with mounted content, make collapsed controls inert, keep headers/columns/editors stable, retain drafts and expansion by user ID through sorting/filtering and refresh, and keep ordinary row clicks separate from editing. Group per-user feature toggles by domain. Distinguish a role's starting template from individual capabilities; show dependency explanations and preserve dependent preferences when parent access is disabled. Pausing account access retains preferences while reducing effective access to zero. Explain fixed owner permissions. Keep avatars visible on idle, hover and selected surfaces in both themes. On mobile, contain table scrolling and keep expanded configuration readable with usable controls.
66. Give webhooks their own configuration and delivery views rather than burying them inside a generic API settings form. Include endpoint name, validated HTTPS URL, enable/pause state, subscribed events, signing-secret handling, timeout and retry policy. Require at least one event for an enabled endpoint. Mask secrets by default, provide named reveal/copy controls and show a green tick after copying. Explain signature verification, timestamp freshness and event-ID deduplication without displaying real secrets in a demo. Separate saved endpoint configuration from test-event controls and delivery history. Show loading, delivered, failed and timeout states; inspect payloads with syntax highlighting and offer a clear retry action. Block repeated runs while busy and preserve configuration/drafts through navigation. Label local simulations and never imply that a demo sent a request.
67. Admin references must remain self-contained and usable as reusable examples, including local scripts, styles, preview media, provider SVGs, loaders and attribution. Keep configuration drafts, saved values, read state and operational history separate. Background test completion must update the intended record without injecting stale content into another page after navigation. Reuse shared controls instead of inventing variants per page. Verify navigation, applicable conditional fields, validation, Save/Discard, collapsed/expanded configurations, loading and result states, both themes and mobile screenshots; describe backend-dependent actions honestly.
68. When building configuration pages inside a studio layout, reuse the approved [studio configuration reference](references/studio-configuration.md) and bundled Shappy example in `assets/studio-configuration/`. Use the main workspace for the live result and a right inspector for its configuration, retaining the shared header, navigation, outer frame and panel transitions. Keep the preview visible while changing controls. Group inspector settings by purpose, with compact aligned labels, inputs and actions; do not turn a visual configuration task into a long admin form. Show only the controls and toolbar actions relevant to the selected view. Adapt branding, colour and content to the app while retaining the structure and interactions. The bundled specimen is named Shappy throughout its pages, previews, tooltips, generated code and demo identifiers; keep example naming consistent and do not leak an upstream product name into the reusable UI. For ordinary Settings inside a studio, keep the outer frame visible and place section navigation beside the form inside the main workspace. Hide the preview inspector for this view. Group navigation by domain with a short group heading, a 1 px gap between adjacent items and a larger gap between groups. Use headings and space between distinct form sections, and thin inset separators only between related rows on the same surface. Keep the navigation/content divider structural. Do not add decorative card borders. Size form columns from the available content width, not only the viewport width; allow labels and controls to shrink safely, and stack controls below labels when the content area is narrow. Fields must remain inside their surface without horizontal scrolling or excessive label wrapping. Preserve section deep links, drafts and validation through navigation. Apply rule 30 for Save/Discard. Keep mock examples clearly local, with representative text, number, time, slider, toggle, choice and conditional controls. Verify expanded and collapsed outer rails, narrow content areas, both themes and the embedded reference.
69. For configuration playgrounds, retain a subtle dotted canvas behind spatial previews, including the playground and applicable logo hero. Use a repeating SVG dot tile with theme-aware contrast, consistent spacing and no background gradients. Keep ordinary forms and inspector controls on flat surfaces. Provide realistic interactive targets and a focused set of state and behaviour controls in the inspector. Reuse the reference's presets, reset/copy actions, sliders with labelled numeric outputs, validated colour picker plus hex field, and magnified/actual-size previews where appropriate. Let users exercise idle, thinking, active and transition states without losing configuration. Keep play, pause/cancel and applicable keyboard shortcuts discoverable, show useful status feedback, and respect reduced motion. Use realistic component examples rather than decorative mock controls that do nothing.
70. For logo and brand configuration, keep a large live preview in the workspace and inspect the same draft across horizontal/stacked lockups, light/dark surfaces, app-icon sizes and colour/monochrome variants. Reuse the app's supplied mark or custom SVG and shared brand tokens so all previews update together. Put name, colour, geometry and applicable motion/effect controls in the right inspector, with clear reset and SVG/configuration export actions. Keep original SVG geometry and attribution where the asset is sourced. Verify small-size legibility and centring; glow and motion are optional product choices, not universal brand requirements.
71. For embed/component configuration, preview the component inside a representative host page and isolate the preview where appropriate. Group inspector controls into Presentation, Behaviour, Theme and integration/export sections. Offer applicable layouts such as docked panel, floating corner, typing island and side-by-side, with relevant width, visibility and behaviour controls. Provide colour presets and validated custom values, show generated integration code with syntax highlighting, and provide copy feedback with a green tick. Keep preview and generated configuration consistent. Validate cross-frame messages by origin and source. Clearly distinguish a scripted UI preview from a real model, external integration or production service; do not require the bundled example SDK when applying this layout to another product.
72. A studio configuration preview updates immediately from the draft; that visual feedback must not silently commit production settings. Apply rule 30 to actual editable configurations, retain drafts across view changes and panel hiding, and keep Save/Discard outside the preview's geometry. Reset and presets update the draft; export copies the currently displayed valid configuration. If a sandbox remembers preview preferences automatically, identify that local behaviour separately from product persistence. Preserve route, active view and relevant configuration through refresh, keep hidden views and panels non-interactive, and verify preview/control synchronisation, keyboard operation, export, both themes and mobile layouts without clipping.
73. Keep application authentication outside the admin/operator shell. Sign-in, sign-up, password recovery and authentication challenges use standalone public routes and a minimal authentication layout, without admin navigation, operational toolbars, inspectors or protected content. The admin shell renders only after session validation succeeds; show a stable neutral loading state while validation is pending. Guard protected routes before mounting the shell and redirect unauthenticated users to sign-in, preserving a validated same-origin return destination. After authentication, return to that destination or the default workspace. On logout or session expiry, leave the protected shell and show the standalone authentication flow. Account/security settings and model-provider connection credentials remain in their appropriate authenticated configuration pages; they are not application sign-in forms. Client-side guards do not replace server/API authorisation. For a self-contained demo, clearly identify simulated authentication.
